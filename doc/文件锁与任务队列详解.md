## 一、文件锁机制的底层实现

### 1.1 为什么选择文件锁？

在分布式系统中，常见的锁方案有：

| 锁类型 | 优点 | 缺点 | 适用场景 |
|--------|------|------|----------|
| **内存锁** | 性能最高 | 只能单进程内有效 | 单进程应用 |
| **Redis 锁** | 支持分布式 | 需要额外服务，增加复杂度 | 分布式系统 |
| **数据库锁** | 持久化可靠 | 性能开销大 | 需要事务保证的场景 |
| **文件锁** | 简单可靠，无需额外依赖 | 仅适合单机多进程 | 单机部署场景 |

**这个项目选择文件锁的原因**：

1. ✅ **简单可靠**：无需额外依赖（Redis、数据库等）
2. ✅ **原子性保证**：操作系统级别的原子操作
3. ✅ **故障恢复**：进程崩溃后锁文件仍存在，可通过超时机制恢复
4. ✅ **适合场景**：单机部署的 Node.js 应用

### 1.2 原子性保证：`fs.open("wx")` 的魔法

**核心代码** (`util/index.ts:137`):

```typescript
fs.open(lockFile, "wx", async (err, fd) => {
  if (err) {
    if (err.code === "EEXIST") {
      // 文件已存在，说明锁被占用
      return resolve(false);
    }
  }
  // 成功创建文件，获取锁成功
})
```

#### `"wx"` 模式的原子性

- `"w"` = write（写入模式）
- `"x"` = exclusive（独占创建模式）
- **关键特性**：如果文件已存在，操作立即失败，返回 `EEXIST` 错误

这个操作映射到操作系统的 `open()` 系统调用，使用 `O_CREAT | O_EXCL` 标志：

```c
// 底层系统调用（伪代码）
int fd = open(path, O_CREAT | O_EXCL | O_WRONLY, 0644);
// 如果文件已存在，返回 -1 并设置 errno = EEXIST
```

#### 为什么是原子的？

**原子性的本质**：

```
非原子操作（错误示例）：
1. 检查文件是否存在  ← 进程A执行
2. 如果不存在，创建文件 ← 进程B也执行 ← 竞态条件！

原子操作（fs.open("wx")）：
1. 内核级别的单一操作：检查+创建
2. 即使1000个进程同时执行，内核保证只有一个成功
3. 其他进程立即收到 EEXIST 错误
```

**并发场景演示**：

```
时间线：进程A、B、C 同时尝试获取锁

t=0ms:
  进程A: fs.open(lockFile, "wx") → 发送系统调用
  进程B: fs.open(lockFile, "wx") → 发送系统调用
  进程C: fs.open(lockFile, "wx") → 发送系统调用

t=1ms (内核处理):
  内核: 接收到3个请求，按到达顺序处理
  内核: 进程A的请求先到 → 创建文件成功 → 返回 fd=3
  内核: 进程B的请求 → 文件已存在 → 返回 EEXIST
  内核: 进程C的请求 → 文件已存在 → 返回 EEXIST

t=2ms (应用层处理):
  进程A: 获取锁成功 ✅
  进程B: 获取锁失败 ❌
  进程C: 获取锁失败 ❌
```

### 1.3 锁的生命周期管理

**锁信息结构** (`util/index.ts:19-24`):

```typescript
interface ProjectLockInfo {
  projectId: string;    // 项目标识
  taskId?: string;      // 任务标识（可选）
  timestamp: number;    // 获取锁的时间戳
  status: "processing" | "queued";  // 状态
}
```

**完整的锁生命周期**：

```
┌─────────────────────────────────────────────────────────┐
│ 1. 获取锁 (acquireLock)                                  │
│    ↓                                                     │
│    fs.open(lockFile, "wx") → 原子创建锁文件              │
│    ↓                                                     │
│ 2. 写入锁信息                                            │
│    ↓                                                     │
│    {projectId, taskId, timestamp, status}                │
│    ↓                                                     │
│ 3. 启动心跳定时器 (startLockHeartbeat)                   │
│    ↓                                                     │
│    setInterval(() => refreshTimestamp(), 15s)            │
│    ├─ 每15秒刷新时间戳                                   │
│    └─ 防止长任务被误判超时                               │
│    ↓                                                     │
│ 4. 执行业务逻辑（翻译任务）                               │
│    ↓                                                     │
│    [翻译可能持续数分钟]                                   │
│    ↓                                                     │
│ 5. 停止心跳 (stopHeartbeat)                              │
│    ↓                                                     │
│    clearInterval(timer)                                  │
│    ↓                                                     │
│ 6. 释放锁 (releaseLock)                                  │
│    ↓                                                     │
│    fs.unlinkSync(lockFile) → 删除锁文件                  │
└─────────────────────────────────────────────────────────┘
```

**代码实现** (`util/index.ts:130-211`):

```typescript
async function acquireLock(
  projectId?: string,
  taskId?: string
): Promise<boolean> {
  return new Promise((resolve, reject) => {
    const lockFile = getLockFilePath(projectId || "unknown");

    // 尝试以独占写入模式创建文件
    fs.open(lockFile, "wx", async (err, fd) => {
      if (err) {
        if (err.code === "EEXIST") {
          // 锁文件已存在，检查是否超时
          try {
            const lockContent = fs.readFileSync(lockFile, "utf-8");
            let lockInfo: ProjectLockInfo;

            try {
              // 尝试解析为JSON格式（新格式）
              lockInfo = JSON.parse(lockContent);
            } catch {
              // 兼容旧格式（纯时间戳）
              const lockTimestamp = parseInt(lockContent, 10);
              if (isNaN(lockTimestamp)) {
                console.warn(`锁文件内容无效，尝试强制删除并重新获取锁`);
                releaseLock(projectId);
                return resolve(await acquireLock(projectId, taskId));
              }

              lockInfo = {
                projectId: "legacy",
                timestamp: lockTimestamp,
                status: "processing",
              };
            }

            const currentTime = Date.now();
            if (currentTime - lockInfo.timestamp > LOCK_TIMEOUT_MS) {
              console.warn(`锁文件已超时，强制删除并重新获取锁`);
              releaseLock(projectId);
              return resolve(await acquireLock(projectId, taskId));
            } else {
              // 锁未超时，获取锁失败
              return resolve(false);
            }
          } catch (readErr: any) {
            console.error(`读取或处理锁文件时发生错误: ${readErr.message}`);
            return reject(readErr);
          }
        }
        console.error(`获取文件锁时发生未知错误: ${err.message}`);
        return reject(err);
      }

      // 成功创建文件，写入锁信息
      const lockInfo: ProjectLockInfo = {
        projectId: projectId || "unknown",
        taskId,
        timestamp: Date.now(),
        status: "processing",
      };
      const lockContent = JSON.stringify(lockInfo);
      fs.write(fd, lockContent, (writeErr) => {
        fs.close(fd, (closeErr) => {
          if (closeErr) console.error("关闭锁文件描述符时发生错误:", closeErr);
        });
        if (writeErr) {
          console.error(`写入锁文件时间戳时发生错误: ${writeErr.message}`);
          releaseLock(projectId);
          return reject(writeErr);
        }
        resolve(true); // 成功获取锁
      });
    });
  });
}
```

**释放锁** (`util/index.ts:217-227`):

```typescript
function releaseLock(projectId?: string): void {
  try {
    const lockFile = getLockFilePath(projectId || "unknown");
    if (fs.existsSync(lockFile)) {
      fs.unlinkSync(lockFile); // 删除锁文件
      console.log(`[${projectId}] 文件锁已释放。`);
    }
  } catch (err) {
    console.error(`[${projectId}] 释放文件锁时发生错误:`, err);
  }
}
```

### 1.4 超时与心跳机制

#### 时间参数设计

**核心参数** (`util/index.ts:6-7`):

```typescript
const LOCK_TIMEOUT_MS = 1000 * 60 * 1;  // 60秒超时
const LOCK_HEARTBEAT_INTERVAL_MS = 15 * 1000;  // 15秒心跳
```

**参数设计原则**：

```
心跳间隔 << 超时时间

15秒 << 60秒

这样可以确保：
- 正常任务：每15秒刷新一次，永远不会超时
- 崩溃任务：60秒后自动释放锁
- 安全边界：即使丢失3-4次心跳，仍然不会超时
```

#### 超时检测逻辑

**代码实现** (`util/index.ts:168-175`):

```typescript
const currentTime = Date.now();
if (currentTime - lockInfo.timestamp > LOCK_TIMEOUT_MS) {
  console.warn(`⚠️ 锁文件已超时 (${
    (currentTime - lockInfo.timestamp) / 1000
  }s)，强制删除并重新获取锁`);
  releaseLock(projectId);
  return resolve(await acquireLock(projectId, taskId)); // 递归重试
}
```

**超时场景分析**：

```
场景1：进程崩溃
t=0s:   进程A获取锁，开始翻译
t=10s:  进程A崩溃 💥（锁文件仍然存在）
t=70s:  进程B尝试获取锁
        → 检查锁文件：timestamp = 0s
        → 当前时间 - 0s = 70s > 60s
        → 判定超时，强制删除锁
        → 进程B成功获取锁 ✅

场景2：网络延迟导致任务超长
t=0s:   进程A获取锁，开始翻译
t=0-90s: 翻译进行中（网络慢）
        → 心跳每15秒刷新时间戳
        → 锁始终有效
t=90s:  翻译完成，释放锁 ✅
```

#### 心跳刷新逻辑

**刷新时间戳** (`util/index.ts:275-306`):

```typescript
function refreshLockTimestamp(projectId?: string): void {
  try {
    const lockFile = getLockFilePath(projectId || "unknown");
    if (!fs.existsSync(lockFile)) return;

    const content = fs.readFileSync(lockFile, "utf-8");
    let lockInfo: ProjectLockInfo = JSON.parse(content);

    // 更新时间戳
    lockInfo.timestamp = Date.now();
    fs.writeFileSync(lockFile, JSON.stringify(lockInfo));
  } catch (err) {
    console.error("刷新锁文件时间戳失败:", err);
  }
}
```

**启动心跳定时器** (`util/index.ts:312-321`):

```typescript
function startLockHeartbeat(projectId?: string): () => void {
  const timer = setInterval(() => {
    refreshLockTimestamp(projectId);
  }, LOCK_HEARTBEAT_INTERVAL_MS);

  // 避免阻止进程退出
  if ((timer as any).unref) {
    (timer as any).unref();
  }

  return () => clearInterval(timer);  // 返回停止函数
}
```

**为什么需要心跳？场景对比**：

```
❌ 没有心跳机制：
t=0s:   任务开始，锁时间戳 = 0
t=70s:  任务仍在执行（正常的长任务）
        新请求到来 → 检查：70s > 60s → 误判超时 → 强制抢占锁
        → 两个进程同时翻译同一项目 → 数据冲突 💥

✅ 有心跳机制：
t=0s:   任务开始，锁时间戳 = 0
t=15s:  心跳刷新，锁时间戳 = 15s
t=30s:  心跳刷新，锁时间戳 = 30s
t=45s:  心跳刷新，锁时间戳 = 45s
t=60s:  心跳刷新，锁时间戳 = 60s
t=70s:  任务仍在执行
        新请求到来 → 检查：70s - 60s = 10s < 60s → 锁有效
        → 新请求加入队列 → 等待当前任务完成 ✅
```

**心跳的使用方式** (`routes/i18n.ts:66, 79-80`):

```typescript
// 获取锁成功后，立即启动心跳
const stopHeartbeat = startLockHeartbeat(projectId);

try {
  // 执行长时间任务
  await runI18nSync({
    projectId,
    uploadedEnJsonContent,
    promoteToCurrent,
    commitId,
  });
} finally {
  // 无论成功失败，都要停止心跳并释放锁
  stopHeartbeat();
  releaseLock(projectId);
}
```

## 二、任务队列机制

### 2.1 队列的数据结构

**队列文件**: `cache/translation_queue.json`

**任务结构** (`util/versioning.ts:274-282`):

```typescript
export interface TranslationTask {
  id: string;                    // 唯一标识: task_${timestamp}_${random}
  projectId: string;             // 项目ID（用于锁隔离）
  uploadedEnJsonContent: string | null;  // 翻译内容
  promoteToCurrent: boolean;     // 是否推广到生产
  commitId: string | null;       // Git commit ID
  timestamp: number;             // 创建时间
  status: "pending" | "processing" | "completed" | "failed";
}
```

**队列是一个 JSON 数组**：

```json
[
  {
    "id": "task_1710251234567_abc123",
    "projectId": "project-A",
    "status": "pending",
    "timestamp": 1710251234567,
    "uploadedEnJsonContent": "{...}",
    "promoteToCurrent": false,
    "commitId": "abc123def"
  },
  {
    "id": "task_1710251234890_def456",
    "projectId": "project-A",
    "status": "processing",
    "timestamp": 1710251234890,
    "uploadedEnJsonContent": "{...}",
    "promoteToCurrent": true,
    "commitId": "def456ghi"
  }
]
```

**为什么使用文件而不是内存？**

| 方案 | 优点 | 缺点 |
|------|------|------|
| 内存队列 | 性能高 | 进程重启丢失数据 |
| 文件队列 | 持久化，重启不丢失 | 性能略低（可接受） |
| 数据库队列 | 功能强大 | 需要额外服务 |

**选择文件队列的原因**：
- ✅ 进程重启后任务不丢失
- ✅ 无需额外依赖
- ✅ 对于翻译任务（非高频操作），性能足够

### 2.2 任务入队：防重复机制

**添加任务** (`util/versioning.ts:288-344`):

```typescript
export async function addTranslationTask(
  task: Omit<TranslationTask, "id" | "timestamp" | "status">
): Promise<string> {
  // 1. 生成唯一任务ID
  const taskId = `task_${Date.now()}_${Math.random()
    .toString(36)
    .substr(2, 9)}`;

  // 2. 读取现有队列
  let queue: TranslationTask[] = [];
  if (fs.existsSync(TRANSLATION_QUEUE_FILE)) {
    const content = fs.readFileSync(TRANSLATION_QUEUE_FILE, "utf8");
    queue = JSON.parse(content);
  }

  // 3. 防重复检查
  const existingTask = queue.find(t =>
    t.projectId === task.projectId &&
    t.commitId === task.commitId &&
    t.status === "pending"
  );

  if (existingTask) {
    console.log(`项目已有待处理任务，跳过重复添加`);
    return existingTask.id;  // 返回已存在的任务ID
  }

  // 4. 添加新任务
  const fullTask: TranslationTask = {
    ...task,
    id: taskId,
    timestamp: Date.now(),
    status: "pending",
  };
  queue.push(fullTask);

  // 5. 持久化到文件
  fs.writeFileSync(TRANSLATION_QUEUE_FILE, JSON.stringify(queue, null, 2));

  return taskId;
}
```

**防重复的意义**：

```
场景：用户快速点击"翻译"按钮3次（同一个 commit）

请求1 (t=0ms):
  → 获取锁成功
  → 开始翻译

请求2 (t=100ms):
  → 获取锁失败
  → 检查队列：无相同任务
  → 添加到队列: task_001 (pending)
  → 返回: "任务已加入队列，任务ID: task_001"

请求3 (t=200ms):
  → 获取锁失败
  → 检查队列：发现 task_001 (projectId=A, commitId=abc, status=pending)
  → 跳过添加
  → 返回: "任务已加入队列，任务ID: task_001"

结果：
- 只有2个任务（1个执行中 + 1个队列中）
- 避免了重复翻译同一个 commit
```

**防重复的判断条件**：

```typescript
t.projectId === task.projectId &&  // 同一项目
t.commitId === task.commitId &&    // 同一提交
t.status === "pending"             // 待处理状态
```

**为什么只检查 pending 状态？**

```
场景：commit A 已经翻译完成，现在要重新翻译

队列状态：
[
  {id: "task_001", projectId: "A", commitId: "abc", status: "completed"}
]

新请求：projectId="A", commitId="abc"
检查：找不到 status="pending" 的任务
结果：允许添加新任务 ✅

原因：用户可能需要重新翻译已完成的提交（例如修复翻译错误）
```

### 2.3 任务出队：状态转换

**获取下一个任务** (`util/versioning.ts:350-380`):

```typescript
export async function getNextTranslationTask(): Promise<TranslationTask | null> {
  if (!fs.existsSync(TRANSLATION_QUEUE_FILE)) {
    return null;
  }

  const content = fs.readFileSync(TRANSLATION_QUEUE_FILE, "utf8");
  const queue: TranslationTask[] = JSON.parse(content);

  // 查找第一个 pending 状态的任务
  const nextTask = queue.find(task => task.status === "pending");

  if (nextTask) {
    // 立即标记为 processing（防止重复处理）
    nextTask.status = "processing";
    fs.writeFileSync(TRANSLATION_QUEUE_FILE, JSON.stringify(queue, null, 2));
    console.log(`[VERSIONING] 获取下一个翻译任务: ${nextTask.id}`);
  }

  return nextTask || null;
}
```

**状态转换流程**：

```
pending → processing → completed
   ↑↓                      ↓
   └──────────────────────┘ (失败时可能回退或标记为 failed)

状态说明：
- pending: 等待处理
- processing: 正在处理
- completed: 处理完成
- failed: 处理失败
```

**为什么要立即标记为 processing？**

```
❌ 没有立即标记的问题：

t=0ms:
  进程A: 读取队列 → 找到 task_001 (pending)
  进程B: 读取队列 → 找到 task_001 (pending)  ← 同一个任务！

t=100ms:
  进程A: 开始处理 task_001
  进程B: 也开始处理 task_001  ← 重复处理，浪费资源

✅ 立即标记的好处：

t=0ms:
  进程A: 读取队列 → 找到 task_001 (pending)
         → 立即标记为 processing
         → 保存到文件

t=50ms:
  进程B: 读取队列 → task_001 已经是 processing
         → 找到 task_002 (pending)
         → 立即标记为 processing
         → 保存到文件

t=100ms:
  进程A: 处理 task_001
  进程B: 处理 task_002  ← 并发处理不同任务 ✅
```

### 2.4 任务状态更新

**更新状态** (`util/versioning.ts:387-412`):

```typescript
export async function updateTranslationTaskStatus(
  taskId: string,
  status: TranslationTask["status"]
): Promise<void> {
  if (!fs.existsSync(TRANSLATION_QUEUE_FILE)) {
    return;
  }

  const content = fs.readFileSync(TRANSLATION_QUEUE_FILE, "utf8");
  const queue: TranslationTask[] = JSON.parse(content);

  const task = queue.find(t => t.id === taskId);
  if (task) {
    task.status = status;
    fs.writeFileSync(TRANSLATION_QUEUE_FILE, JSON.stringify(queue, null, 2));
    console.log(`[VERSIONING] 任务 ${taskId} 状态更新为: ${status}`);
  }
}
```

**状态更新的时机**：

```
1. pending → processing
   时机：getNextTranslationTask() 获取任务时
   位置：util/versioning.ts:368

2. processing → completed
   时机：任务成功完成后
   位置：routes/i18n.ts:515

3. processing → failed
   时机：任务执行失败后
   位置：routes/i18n.ts:522

4. processing → pending
   时机：获取锁失败时回退
   位置：routes/i18n.ts:495
```

**完整的状态机**：

```
        ┌─────────────────────────────────┐
        │                                 │
        │  addTranslationTask()           │
        │                                 │
        └──────────────┬──────────────────┘
                       ↓
                  ┌─────────┐
                  │ pending │  ← 初始状态
                  └─────────┘
                       ↓
        getNextTranslationTask()
                       ↓
                  ┌────────────┐
           ┌─────→│ processing │←─────┐
           │      └────────────┘      │
           │            ↓             │
           │      任务执行中            │
           │            ↓             │
           │      ┌──────┴──────┐     │
           │      ↓             ↓     │
```

## 三、锁与队列的协同工作

### 3.1 完整的请求处理流程

**入口函数** (`routes/i18n.ts:32-99`):

```typescript
async function executeI18nSync(
  uploadedEnJsonContent: string | null,
  projectId: string | null,
  promoteToCurrent: boolean,
  commitId: string | null
) {
  try {
    // 步骤1: 尝试获取项目锁
    const lockAcquired = await acquireLock(projectId || "unknown");

    if (!lockAcquired) {
      // 步骤2a: 获取锁失败 → 加入队列
      console.log(`[${projectId}] 翻译服务忙碌，将任务添加到队列中...`);

      const taskId = await addTranslationTask({
        projectId: projectId || "unknown",
        uploadedEnJsonContent,
        promoteToCurrent,
        commitId,
      });

      const pendingCount = await getPendingTaskCount(projectId);

      return {
        code: 0,
        message: `任务已加入队列。任务ID: ${taskId}，队列位置: ${pendingCount}`,
      };
    }

    // 步骤2b: 获取锁成功 → 直接执行
    console.log(`[${projectId}] 启动新的多语言同步任务...`);

    // 步骤3: 启动心跳续租
    const stopHeartbeat = startLockHeartbeat(projectId);

    // 步骤4: 异步执行翻译任务
    (async () => {
      try {
        await runI18nSync({
          projectId,
          uploadedEnJsonContent,
          promoteToCurrent,
          commitId,
        });
        console.log(`[${projectId}] 多语言同步任务完成。`);
      } catch (e: any) {
        console.error(`[${projectId}] 多语言同步任务失败:`, e?.message);
      } finally {
        // 步骤5: 清理资源
        stopHeartbeat();
        releaseLock(projectId);

        // 步骤6: 处理队列中的下一个任务
        await processNextQueuedTask();
      }
    })();

    return {
      code: 0,
      message: "新的多语言同步任务已提交至后台",
    };
  } catch (e: any) {
    releaseLock(projectId);
    return {
      code: 500,
      message: e?.message || "多语言同步任务提交失败",
      error: e?.message,
    };
  }
}
```

### 3.2 队列任务处理流程

**处理队列任务** (`routes/i18n.ts:477-538`):

```typescript
async function processNextQueuedTask(): Promise<void> {
  try {
    // 1. 获取下一个待处理任务
    const nextTask = await getNextTranslationTask();

    if (!nextTask) {
      console.log("[QUEUE] 队列中没有待处理的任务");
      return;
    }

    console.log(`[QUEUE] 开始处理队列中的任务: ${nextTask.id}`);

    // 2. 尝试获取锁
    const lockAcquired = await acquireLock(nextTask.projectId, nextTask.id);
    if (!lockAcquired) {
      console.log(`[QUEUE] 无法获取锁，任务 ${nextTask.id} 将等待下次处理`);
      // 将任务状态重置为 pending
      await updateTranslationTaskStatus(nextTask.id, "pending");
      return;
    }

    // 3. 开启锁心跳
    const stopHeartbeat = startLockHeartbeat(nextTask.projectId);

    try {
      // 4. 执行翻译任务
      await runI18nSync({
        projectId: nextTask.projectId,
        uploadedEnJsonContent: nextTask.uploadedEnJsonContent,
        promoteToCurrent: nextTask.promoteToCurrent,
        commitId: nextTask.commitId,
      });

      console.log(`[QUEUE] 任务 ${nextTask.id} 处理完成`);
      await updateTranslationTaskStatus(nextTask.id, "completed");
      await removeTranslationTask(nextTask.id);
    } catch (error: any) {
      console.error(`[QUEUE] 任务 ${nextTask.id} 处理失败:`, error?.message);
      await updateTranslationTaskStatus(nextTask.id, "failed");
      // 失败的任务不移除，可以稍后重试
    } finally {
      // 5. 清理资源
      stopHeartbeat();
      releaseLock(nextTask.projectId);

      // 6. 递归处理下一个任务（延迟1秒）
      setTimeout(() => {
        processNextQueuedTask().catch((err) => {
          console.error("[QUEUE] 处理下一个任务时发生错误:", err);
        });
      }, 1000);
    }
  } catch (error) {
    console.error("[QUEUE] 处理队列任务时发生错误:", error);
  }
}
```

## 四、边界情况处理

### 4.1 进程崩溃恢复

**问题**：如果进程在持有锁时崩溃，锁文件不会被删除，导致死锁。

**解决方案**：超时机制

```typescript
// 检查锁是否超时
if (currentTime - lockInfo.timestamp > LOCK_TIMEOUT_MS) {
  console.warn(`锁文件已超时，强制删除并重新获取锁`);
  releaseLock(projectId);
  return resolve(await acquireLock(projectId, taskId));
}
```

**场景演示**：

```
t=0s:   进程A获取锁，开始翻译
t=10s:  进程A崩溃 💥
        锁文件仍然存在：{timestamp: 0, projectId: "A"}

t=70s:  进程B尝试获取锁
        → 读取锁文件：timestamp = 0
        → 当前时间 - 0 = 70s > 60s
        → 判定超时
        → 删除锁文件
        → 重新获取锁成功 ✅

结果：系统自动恢复，不需要人工干预
```

### 4.2 锁文件损坏

**问题**：锁文件内容被意外修改或损坏。

**解决方案**：异常处理 + 强制删除

```typescript
try {
  lockInfo = JSON.parse(lockContent);
} catch {
  // 兼容旧格式或处理损坏的文件
  const lockTimestamp = parseInt(lockContent, 10);
  if (isNaN(lockTimestamp)) {
    console.warn(`锁文件内容无效，尝试强制删除并重新获取锁`);
    releaseLock(projectId);
    return resolve(await acquireLock(projectId, taskId));
  }
}
```

### 4.3 队列文件损坏

**问题**：队列文件被意外修改或损坏。

**解决方案**：异常处理 + 重新初始化

```typescript
try {
  if (fs.existsSync(TRANSLATION_QUEUE_FILE)) {
    const content = fs.readFileSync(TRANSLATION_QUEUE_FILE, "utf8").trim();
    if (content) {
      queue = JSON.parse(content);
    }
  }
} catch (err) {
  console.warn("[VERSIONING] Failed to parse translation_queue.json, reinitializing...", err);
  queue = [];  // 重新初始化为空队列
}
```

### 4.4 获取锁失败后的队列任务处理

**问题**：队列任务获取锁失败时如何处理？

**解决方案**：回退状态，等待下次处理

```typescript
const lockAcquired = await acquireLock(nextTask.projectId, nextTask.id);
if (!lockAcquired) {
  console.log(`[QUEUE] 无法获取锁，任务 ${nextTask.id} 将等待下次处理`);
  // 将任务状态重置为 pending
  await updateTranslationTaskStatus(nextTask.id, "pending");
  return;
}
```

**为什么要回退状态？**

```
场景：项目A有两个任务在队列中

队列状态：
[
  {id: "task_001", projectId: "A", status: "pending"},
  {id: "task_002", projectId: "A", status: "pending"}
]

t=0s:
  processNextQueuedTask() 被调用
  → 获取 task_001，标记为 processing
  → 尝试获取锁A → 失败（锁被其他进程占用）
  → 回退状态：task_001 → pending
  → 返回

t=60s:
  锁A被释放
  → processNextQueuedTask() 再次被调用
  → 获取 task_001（仍然是 pending）
  → 尝试获取锁A → 成功 ✅
  → 执行任务

如果不回退状态：
  task_001 会一直保持 processing 状态
  → 下次调用 getNextTranslationTask() 会跳过它
  → 任务永远不会被执行 ❌
```

### 4.5 心跳失败处理

**问题**：心跳刷新时可能遇到文件系统错误。

**解决方案**：捕获异常，记录日志，不中断主流程

```typescript
function refreshLockTimestamp(projectId?: string): void {
  try {
    const lockFile = getLockFilePath(projectId || "unknown");
    if (!fs.existsSync(lockFile)) return;

    const content = fs.readFileSync(lockFile, "utf-8");
    let lockInfo: ProjectLockInfo = JSON.parse(content);

    lockInfo.timestamp = Date.now();
    fs.writeFileSync(lockFile, JSON.stringify(lockInfo));
  } catch (err) {
    console.error("刷新锁文件时间戳失败:", err);
    // 不抛出异常，避免中断主流程
  }
}
```

**为什么不抛出异常？**

```
如果心跳刷新失败并抛出异常：
  → 定时器中断
  → 后续心跳停止
  → 锁时间戳不再更新
  → 可能被误判为超时

捕获异常并记录日志：
  → 定时器继续运行
  → 下次心跳可能成功
  → 即使连续失败几次，仍有机会恢复
```

## 五、性能与可靠性分析

### 5.1 性能特点

**文件锁的性能**：

| 操作 | 时间复杂度 | 说明 |
|------|-----------|------|
| 获取锁 | O(1) | 系统调用，毫秒级 |
| 释放锁 | O(1) | 删除文件，毫秒级 |
| 检查超时 | O(1) | 读取文件 + 时间比较 |
| 心跳刷新 | O(1) | 读写文件，毫秒级 |

**队列的性能**：

| 操作 | 时间复杂度 | 说明 |
|------|-----------|------|
| 添加任务 | O(n) | 需要遍历队列检查重复 |
| 获取任务 | O(n) | 需要查找第一个 pending 任务 |
| 更新状态 | O(n) | 需要查找任务 |

**性能瓶颈**：

```
当队列中有大量任务时（例如 1000+ 个）：
- 每次操作都需要读取整个文件
- 需要遍历整个数组

优化方案（如果需要）：
1. 使用数据库（SQLite）替代文件
2. 使用索引加速查询
3. 定期清理已完成的任务
```

### 5.2 可靠性保证

**1. 原子性**

```
✅ 锁获取：fs.open("wx") 是原子操作
✅ 文件写入：fs.writeFileSync() 是原子操作（在大多数文件系统上）
⚠️ 队列操作：读取-修改-写入不是原子的（但对于翻译场景可接受）
```

**2. 持久性**

```
✅ 锁信息：写入文件，进程重启后仍然存在
✅ 队列任务：写入文件，进程重启后不丢失
✅ 翻译缓存：写入文件，持久化保存
```

**3. 故障恢复**

```
✅ 进程崩溃：超时机制自动恢复（60秒）
✅ 文件损坏：异常处理 + 重新初始化
✅ 锁泄漏：超时机制防止死锁
```

**4. 并发安全**

```
✅ 不同项目：完全隔离，可以并发
✅ 同一项目：串行执行，避免冲突
⚠️ 队列操作：文件级别的并发控制（依赖文件系统）
```

### 5.3 系统限制

**1. 单机限制**

```
❌ 不支持多机部署
   原因：文件锁只在单机内有效

如果需要多机部署：
→ 使用 Redis 锁
→ 使用数据库锁
→ 使用分布式锁服务（如 etcd）
```

**2. 文件系统依赖**

```
⚠️ 依赖文件系统的原子性保证
   大多数现代文件系统（ext4, APFS, NTFS）都支持
   但在网络文件系统（NFS）上可能有问题
```

**3. 性能限制**

```
⚠️ 队列操作的时间复杂度为 O(n)
   当队列中有大量任务时性能下降

建议：
- 定期清理已完成的任务
- 如果队列长度超过 1000，考虑使用数据库
```

### 5.4 最佳实践

**1. 锁的使用**

```typescript
// ✅ 正确：使用 try-finally 确保锁被释放
const lockAcquired = await acquireLock(projectId);
if (lockAcquired) {
  const stopHeartbeat = startLockHeartbeat(projectId);
  try {
    await doWork();
  } finally {
    stopHeartbeat();
    releaseLock(projectId);
  }
}

// ❌ 错误：忘记释放锁
const lockAcquired = await acquireLock(projectId);
if (lockAcquired) {
  await doWork();
  // 如果 doWork() 抛出异常，锁永远不会被释放
}
```

**2. 心跳的使用**

```typescript
// ✅ 正确：立即启动心跳
const stopHeartbeat = startLockHeartbeat(projectId);
try {
  await longRunningTask();
} finally {
  stopHeartbeat();  // 确保心跳停止
}

// ❌ 错误：忘记停止心跳
const stopHeartbeat = startLockHeartbeat(projectId);
await longRunningTask();
// 如果忘记调用 stopHeartbeat()，定时器会一直运行
```

**3. 队列的使用**

```typescript
// ✅ 正确：处理完成后递归处理下一个任务
try {
  await processTask();
} finally {
  releaseLock();

// ❌ 错误：忘记处理下一个任务

  await processTask();
} finally {
  releaseLock();

}
```

## 六、总结

### 核心设计思想

1. **简单可靠**：使用文件系统特性，无需额外依赖
2. **原子性保证**：利用操作系统级别的原子操作
3. **故障恢复**：超时机制 + 心跳续租
4. **项目隔离**：每个项目独立的锁，支持并发
5. **持久化**：锁和队列都持久化到文件

### 关键技术点

- **fs.open("wx")**：原子性的锁获取
- **超时机制**：防止死锁（60秒）
- **心跳续租**：防止误判（15秒）
- **队列持久化**：进程重启不丢失任务
- **防重复机制**：避免重复翻译

### 适用场景

✅ 适合：
- 单机部署的应用
- 中低频率的操作（翻译、构建等）
- 需要简单可靠的并发控制

❌ 不适合：
- 多机分布式部署
- 高频率的操作（每秒数千次）
- 需要复杂的队列功能（优先级、延迟等）

### 面试要点

1. **原子性**：解释 fs.open("wx") 的原子性保证
2. **超时与心跳**：解释为什么需要两个机制配合
3. **项目隔离**：解释如何实现不同项目并发、同项目串行
4. **故障恢复**：解释如何处理进程崩溃、文件损坏等异常
5. **性能权衡**：解释为什么选择文件而不是内存或数据库
